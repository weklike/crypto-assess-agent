# 正式评测数据调研方案

版本 v1 · 2026-09-25 · 配合 `docs/实施计划.md`（T02、T05、T09、T15、T16）与 `docs/PROGRESS.md` 使用

## 0. 总体说明

### 0.1 为什么不能复用 fixtures

`data/fixtures/` 下的文件都基于 CC 自拟的“仿标准”（`FIX/T 0001-2026`，36 条虚构条款），只用来证明流水线能跑通：

| 数据 | fixtures 现状 | 不能用于正式评测的原因 |
| --- | --- | --- |
| 规范化标准 | 36 条虚构条款 | 系统要回答的是真实标准，条款号也必须真实 |
| 检索评测集 | 15 条，引用的是 `FIX/T` 条款 | gold_refs 必须存在于真实条款库 |
| 题库样本 | 6 道自拟题，准确率 100% | 题目太简单，测不出任何东西 |
| 评分 golden | 32 例，按测试规则手算 | 在 `scoring.v1` 下只有 26/32 一致；而且是用自己的理解检验同一份规则，没有独立参照 |
| 模拟系统 | 1 个系统，只写了 2 条预期差距 | 预期没列全，误报率失真；预期结果按约定只能由仓库所有者填写 |

### 0.2 调研工具的使用边界

- **可以**：用工具定位官方来源、发布日期、现行版本、标准结构、行业场景和方法论。
- **不可以**：把标准原文、考核题库原文粘贴给外部 AI 工具或在线服务（版权与数据边界，见 `docs/decisions.md` 的“数据边界”一节）。原文只放在 `data/raw/`、`data/private/`，在本地处理。
- **结论必须是你的**：条款是否为“要求”、层面与等级、合规判断、预期差距项、评分算例，都由你确认；工具给出的内容只作为线索，必须回到官方原文核实。
- 每项调研都要记录来源（名称、链接或出处、访问日期），写进本文末尾的“来源登记”。

### 0.3 顺序与依赖

```text
① 标准原文与规范化 ──┬─→ ② 检索评测集
                    ├─→ ⑤ 模拟被测系统（clause_ref 要用真实条款）
                    └─→ 算法规则表补 clause_refs
③ 题库抽样（独立，可与 ① 并行）
④ 评分 golden 用例（依赖量化评估规则原文，可与 ① 并行）
```

建议投入：① 1.5–2 天，② 1 天，③ 0.5–1 天，④ 0.5–1 天，⑤ 1.5–2 天。

## 1. 规范化标准（T02）

### 1.1 产出

| 文件 | 位置 | 进 git |
| --- | --- | --- |
| 原始 PDF | `data/raw/GB-T-39786-2021.pdf`、`data/raw/GB-T-43206-2023.pdf` | 否 |
| 规范化文件 | `data/normalized/GB-T-39786-2021.md`、`data/normalized/GB-T-43206-2023.md` | 否 |
| 抽查记录与条款数 | `docs/PROGRESS.md` T02、T03 行 | 是 |

### 1.2 要回答的问题

1. GB/T 39786-2021、GB/T 43206-2023 的现行状态（是否有修改单、是否被替代）、发布与实施日期。
2. 合法获取途径：国家标准全文公开系统在线阅读、学校或单位的标准数据库、购买纸质或电子版。哪种途径能拿到可提取文字的 PDF？
3. 两份标准的章节结构：哪些章是“要求”（测评指标），哪些是范围、术语、附录？附录是规范性还是资料性？
4. GB/T 39786 中各条要求在第一至第四级上的适用与强度（应/宜/可）怎样表达？本项目的 `levels` 只记录“是否适用”，强度信息要不要写进正文？
5. GB/T 43206 的条款以“测评指标 / 测评对象 / 测评实施 / 结果判定”组织时，哪些部分标 `type: 测评`，哪些标 `说明`？
6. 标准中的表格（如按等级列出的要求表）如何按“一行一条”转成文本？

### 1.3 检索与工具提示词（只问结构和出处，不上传原文）

- “GB/T 39786-2021 信息安全技术 信息系统密码应用基本要求 现行状态 修改单 实施日期”
- “GB/T 43206-2023 信息系统密码应用测评要求 与 GM/T 0115-2021 的关系”
- “国家标准全文公开系统 GB/T 39786-2021 在线阅读”
- 给调研工具的提示词：
  > 请调研国家标准 GB/T 39786-2021 和 GB/T 43206-2023：①现行状态与实施日期；②官方或合法获取途径；③章节结构（列出各章标题与用途，不需要条款原文）；④要求条款在不同安全等级上的表达方式（应/宜/可、适用等级的写法）；⑤每项结论给出处链接。不要编造条款内容，拿不到出处就注明“未找到”。

### 1.4 操作步骤

1. 取得 PDF 放进 `data/raw/`，运行 `java -cp target/classes com.cryptoassess.knowledge.tool.NormalizeTool sha256 <pdf>` 记录哈希。
2. `NormalizeTool draft <pdf> "<标准号>" "<标题>"` 生成 `data/normalized/<名>.draft.md`。
3. 逐章核对：断行、编号、表格；删除没有编号的标题（前言、引言）；附录顶层写作 `# A 标题`。
4. 给“要求”类条款补元数据，紧跟标题下一行：
   `<!-- layer: 网络和通信 | levels: 1,2,3,4 | type: 要求 -->`
   `layer` 只能取八个安全层面；`levels` 用升序列表；`type` 取 要求 / 测评 / 说明 / 术语。
   **注意**：评估工作流只把 `type: 要求` 且层面、等级都匹配的条款当作测评指标，标注是否齐全，直接决定差距分析的覆盖面。
5. 改名为 `.md`，运行 `NormalizeTool lint`，直到 0 个问题。

### 1.5 验收

- 两份文件 lint 0 个问题。
- 随机抽查 50 条，与原文逐字一致；标题编号、层面、等级正确（抽查清单记在 PROGRESS.md）。
- 统计每个层面、每个等级的“要求”条款数，与标准目录对照，没有漏标。
- 导入后（`POST /api/kb/documents`），条款数写进 PROGRESS.md。

## 2. 检索评测集（T05）

### 2.1 产出

`eval/datasets/retrieval_queries.v1.jsonl`：至少 80 条，目标 150 条；进 git。

### 2.2 要回答的问题

1. 实际工作中，系统运营方和测评人员会怎样提问？每个安全层面的高频问题有哪些？
2. 同一个意思，有哪些口语说法、行业黑话、缩写（如“国密改造”“密改”“USBKey”“签名验签”）？
3. 哪些问题天然对应多条条款（如“数据库加密”同时涉及存储机密性、密钥管理）？

### 2.3 调研方法

- 来源优先级：你自己的工作记录与经验 → 行业公开的密评常见问题、培训材料的问题列表（只借鉴问法，不抄答案）→ 测评报告公开模板中的问题描述。
- 检索词：“密评 常见问题”“商用密码应用安全性评估 常见问题 解答”“密码应用方案 评审 常见问题”“国密改造 常见问题”。
- 给调研工具的提示词：
  > 请整理商用密码应用安全性评估（密评）中系统运营方和测评人员的常见提问，按八个安全层面（物理和环境、网络和通信、设备和计算、应用和数据、管理制度、人员管理、建设运行、应急处置）分类，每类 15–20 条，写成真实工作中的口语问法；另列出常见的同义说法和缩写。只给问题，不要给条款号和答案，并注明问法的出处类型。

### 2.4 编写与标注规则

- 构成：`colloquial`（口语）、`paraphrase`（对条款的改写）、`keyword`（关键词）各约三分之一；八个层面都要覆盖，技术层面适当多一些。
- 每条字段：`id`、`query`、`gold_refs`（数组）、`style`、`layer`、`level`（可空）、`note`。
- 对应多条条款时，要把相关条款全部标进 `gold_refs`，否则召回率会被低估。
- 用标注工具（只追加）：
  `java -jar target/crypto-assess-agent-0.0.1-SNAPSHOT.jar --spring.profiles.active=eval --eval.tool=annotate --eval.dataset=v1`
- 可选：让 CC 根据条款生成候选改写问句，你筛选改写后再标注；报告会注明合成问句的比例（合成问句偏向向量检索）。

### 2.5 验收

- `--eval.tool=validate --eval.dataset=v1` 通过（id 唯一、gold_refs 都存在、三种问法都有）。
- 三种问法各约三分之一；每个层面至少 5 条。
- 你随机抽查 10 条标注无误。

## 3. 题库抽样（T09）

### 3.1 产出（全部不进 git）

`data/private/qa_bank.txt` → `qa_bank.jsonl` → `qa_bank_sample.v1.jsonl`（约 200 题）

### 3.2 要回答的问题

1. 官方考核参考题库的发布页面、版本、发布日期、文件格式（OFD）与题量。
2. 题型构成（单选、多选、判断）以及各题型的数量。
3. 答案在文件中如何给出（题后、每节末尾，还是单独的答案表）？这决定了导出的文本需要怎样整理，才能被 `QaBankParser` 识别。
4. 使用限制：题库的知识产权与使用范围说明（本项目只在本地用于评测，输出只记录题号和对错）。

### 3.3 调研方法

- 来源：国家密码管理局网站（开发计划 §8.1 已给出链接），核对是否有更新版本。
- 检索词：“商用密码 考核 参考题库 国家密码管理局 发布”“商用密码应用安全性评估 人员考核 题库”。
- 给调研工具的提示词（只问元信息）：
  > 请查找国家密码管理局发布的商用密码应用安全性评估人员考核参考题库：发布页面链接、发布日期、版本、文件格式、题型与题量说明、使用范围声明。不要下载或转述题目内容。

### 3.4 操作步骤

1. 下载 OFD 放进 `data/private/`，用 OFD 阅读器导出为文本 `qa_bank.txt`。
2. 整理文本版式，使其符合解析器要求：题型小标题（一、单项选择题）、题号（`1．`）、选项（`A．…`，可同行）、答案行（`答案：AB` / `答案：正确`）。
3. 转换：
   ```bash
   ./mvnw -q compile dependency:build-classpath -Dmdep.outputFile=target/classpath.txt
   CP="target/classes:$(cat target/classpath.txt)"
   java -cp "$CP" com.cryptoassess.eval.qabank.QaBankTool convert data/private/qa_bank.txt data/private/qa_bank.jsonl
   ```
   有行号报错就修改文本后重跑（先删掉输出文件，工具不覆盖）。
4. 抽查 20 题（题干、选项、答案与原件一致）。
5. 抽样：`QaBankTool sample data/private/qa_bank.jsonl data/private/qa_bank_sample.v1.jsonl 200 20260924`。

### 3.5 验收

- convert 0 个问题，或剩余问题都有记录的原因。
- 抽查 20 题无误；抽样的题型比例与全库一致。
- 仓库里不出现任何题目原文（`git status` 中看不到 `data/private/`）。

## 4. 评分 golden 用例（T15）

### 4.1 产出

`src/test/resources/scoring_golden.v1.yaml`：至少 30 例；进 git。格式同 `scoring_golden.test.yaml`：

```yaml
cases:
  - id: o01 规则示例一
    findings: [[对象, 应用和数据, <clause_ref>, 部分符合], ...]
    total: "62.50"
    layers: {应用和数据: "0.50"}
    objects: {对象: "0.50"}
```

### 4.2 要回答的问题

1. 现行《商用密码应用安全性评估量化评估规则》的版本、发布机构与实施日期；是否已被新版替代？
2. 规则中的计算方法：判定结果的分值、测评单元（D/A/K）的含义与计分、指标得分如何从多个测评对象汇总（平均还是取最低）、层面权重、总分公式、不适用项处理、舍入方式。
3. 高风险项的认定与对得分或结论的影响。
4. 规则中是否给出算例？有几个？
5. 上述每一点与 `rules/scoring.v1.yaml` 是否一致？不一致的要么改 YAML（新建 v2），要么在 decisions.md 记录为已知差异。

### 4.3 调研方法

- 来源：国家密码管理局或其授权机构发布的规则原文；行业培训材料只作辅助理解，结论以原文为准。
- 检索词：“商用密码应用安全性评估量化评估规则 现行版本”“密评 量化评估 得分 计算 公式”“密评 高风险项 判定”。
- 给调研工具的提示词：
  > 请调研《商用密码应用安全性评估量化评估规则》的现行版本：发布机构与日期、得分计算方法（判定结果分值、测评单元 D/A/K、多个测评对象如何汇总、层面权重、总分公式、不适用处理、舍入）、高风险项规则，以及规则中是否包含算例。每一点都要给出处；只概括方法，不要长段摘抄原文。

### 4.4 编写方法

- 第一部分（约 10–15 例）：规则原文的官方算例，逐一转成 findings 与期望值。这一部分是独立参照，最重要。
- 第二部分（约 15–20 例）：你按 `scoring.v1.yaml` 手算的边界情况：单层面、多层面、多对象取平均、一个层面全部不适用、全部不适用、四舍五入到两位（如 1/3、2/3）、管理类四个层面各 7.5 的权重。
- 如需要，CC 可以把现有 32 个算术用例按 v1 权重重算一份作为第二部分的初稿，由你逐条核对。
- 运行：`--eval.suite=scoring --eval.dataset=v1`。

### 4.5 验收

- 官方算例全部一致；不一致的要写明原因（例如计算器尚未建模高风险项），并决定是否扩展计算器。
- 总数不少于 30，一致率写进 PROGRESS.md。

## 5. 模拟被测系统（T16，只能由你编写）

### 5.1 产出

`eval/datasets/systems/<编号>.v1.yaml`：10–15 个，其中至少 3 个是电力关基场景；进 git。格式见 `eval/datasets/systems/README.md`。

### 5.2 要回答的问题

1. 典型信息系统的密码应用画像：政务服务、金融、医疗、电力等系统通常有哪些测评对象（Web 服务器、数据库、VPN、堡垒机、门禁、视频监控、业务应用、管理制度文档）？
2. 电力关基场景：电力监控系统、调度自动化、营销、用电信息采集等系统的网络分区与边界防护要求，以及行业对商用密码应用的专门要求或政策文件。
3. 常见的合规做法（国密 SSL/IPSec VPN、服务器密码机、签名验签服务器、智能密码钥匙、国密数字证书），以及常见差距（使用非认可算法、自研算法、密钥硬编码、明文协议运维、门禁无密码技术、缺少管理制度）。
4. 测评实践中“部分符合”和“不符合”的边界通常如何把握？

### 5.3 调研方法

- 来源：GB/T 39786、GB/T 43206 原文（判定依据）；电力行业主管部门公开的安全防护规定与方案；密码产品厂商公开的解决方案白皮书（只用来了解系统架构与常见部署，不作为合规依据）；你自己的项目经验。
- 检索词：“电力监控系统 安全防护 规定 现行”“电力行业 商用密码应用 要求”“关键信息基础设施 商用密码使用管理规定 电力”“等保三级 系统 密码应用方案 示例 架构”。
- 给调研工具的提示词：
  > 请调研电力行业关键信息基础设施（如电力监控系统、调度自动化系统、营销系统、用电信息采集系统）的典型网络架构、安全分区、主要设备与软件组件，以及公开的商用密码应用政策和常见国密改造做法。输出每类系统的“测评对象清单”和“典型密码措施”，每项给出处；不要给出合规结论。

### 5.4 编写方法（每个系统）

1. 系统信息：`id`、`name`、`level`（多数取 3）、`scenario`（电力关基 / 政务 / 金融 / 医疗 / 通用）、`description`。
2. 测评对象 3–6 个，覆盖技术层面，至少有一个管理层面的对象（如管理制度文档）。`measures` 按 transport / storage / auth / key_mgmt / other 填写。
3. 有意混合三类措施：合规的（SM2/SM3/SM4、认证产品）、明确不合规的（AES、RSA、MD5、明文协议、密钥硬编码）、信息不足的（只写了“有门禁”）。
4. `expected`：对照真实条款，**把全部差距项列全**（不符合、部分符合），每项写 `{object, clause_ref, judgment}`。符合和不适用的不写。列不全会让误报率失真，这是冒烟测试已经暴露的问题。
5. 建议另外在 YAML 注释里写每条预期差距的理由，便于复核误报。

### 5.5 验收

- 10–15 个系统，至少 3 个电力关基；每个系统 `expected` 已列全，并经你自查一遍。
- 运行 `--eval.suite=gap --eval.dataset=v1` 后，报告中的误报逐条复核，复核结论填进报告的“复核结论”列，最终数字写进 PROGRESS.md。
